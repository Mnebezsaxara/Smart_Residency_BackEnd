# ЧАСТЬ 2. АРХИТЕКТУРА IoT — КАК ОБЪЯСНЯТЬ

## Главная схема (выучи на память, рисуй пальцем)

```
NODE-RED           HIVEMQ CLOUD         GO BACKEND          FIREBASE
(симулятор)  →    (MQTT-брокер)   →   (подписчик)    →    (FCM-сервис)
  нажал            получил             обработал           отправил пуш
  кнопку           сообщение           сохранил в БД       на телефоны
```

Итого: **нажал кнопку → пуш на телефоне за ~1-2 секунды**

## Почему именно ЭТОТ стек (главный вопрос комиссии)

### Почему MQTT, а не HTTP?

| Параметр | MQTT | HTTP |
|---|---|---|
| Размер заголовка | **2 байта** | 200-800 байт |
| Соединение | **Одно постоянное TCP** | Каждый раз новый |
| Push с сервера | **Да, нативно** | Нет (нужен SSE/WS) |
| Для IoT | **Создан для этого** | Слишком тяжёлый |

> Говори: «MQTT был создан IBM в 1999 году специально для IoT — для нефтепроводов в пустыне где каждый байт стоил денег. У нас 54 датчика шлют heartbeat каждые 30 секунд — это 54 сообщения по 2 байта заголовка против 54 HTTP-запросов по 800 байт каждый. Разница в 400 раз.»

### Почему HiveMQ, а не свой брокер?

> «HiveMQ Cloud — готовый облачный MQTT-брокер. Бесплатный тариф дал нам: публичный URL, TLS-шифрование, веб-консоль с мониторингом трафика. Альтернатива — поднять Mosquitto в Docker, но это дополнительная инфраструктура которую нужно администрировать. Для дипломного проекта HiveMQ правильный выбор.»

### Почему Node-RED, а не написать скрипт?

> «Node-RED — это визуальный flow-редактор, созданный IBM. Он позволяет без написания кода соединить компоненты: inject-кнопка → function-нода → MQTT-out. Мы используем его для симуляции датчиков: в реальном проекте на этом месте стояли бы физические датчики ESP32/Arduino с прошивкой, которые сами шлют MQTT. Node-RED позволил нам показать живую систему без реального железа.»

### Почему Go для бэка?

> «Go выбрали по трём причинам: горутины, горутины и горутины. У нас в одном процессе параллельно работают: HTTP-сервер (отвечает Flutter), MQTT-подписчик (ловит датчики), OFFLINE-sweeper (горутина каждые 15 сек), SSE-broadcaster (реалтайм для админа). В Node.js это сделать труднее из-за single-thread event-loop, в Python мешает GIL. Go — компилируемый, один бинарник, никаких рантаймов.»

### Почему Firebase FCM, а не свои push?

> «Firebase Cloud Messaging — бесплатный и универсальный: один API для Android, iOS и Web. Альтернатива — поднять свой push-сервер, но это нетривиально. FCM гарантирует доставку даже когда приложение закрыто — Google держит постоянное соединение с устройством.»

### Почему SSE, а не WebSocket?

> «SSE — Server-Sent Events. Нам нужна только одна сторона: сервер шлёт клиенту. SSE работает через обычный HTTP, браузер/Flutter сам переподключается при разрыве. WebSocket — двусторонний канал, сложнее в реализации. Для нашей задачи (обновления сетки датчиков у Админа) SSE — самый простой и правильный выбор.»

# ЧАСТЬ 3. НАШ NODE-RED FLOW (flows.json) — ДЕТАЛЬНО

## Что у нас в flows.json (один таб = один Flow 1)

В файле 4 ноды-кнопки (inject) + 1 function-нода + 1 MQTT-out нода + конфиг брокера.

### Схема нод:

```
[inject "Reset 2/5 Water"] ─────────────────────────────────┐
                                                             │
[inject "Water Alert 2/5"] ─────────────────────────────────┤
                                                             ▼
[inject "Fire Alert 2/3"]  ─────────────────────────────[MQTT out]──▶ HiveMQ:8883
                                                             ▲
[inject "Heartbeat all 54"] ──▶ [function "Build 54 msgs"] ─┘
```

### Каждая нода подробно:

**inject "Water Alert 2/5"**
- Тема: `smartresidency/sensors/2/5/WATER`
- Payload: `{"id":"w-2-5","type":"WATER","entrance_num":2,"floor":5,"status":"ALERT"}`
- Запуск: вручную (кнопка)

**inject "Fire Alert 2/3"**
- Тема: `smartresidency/sensors/2/3/SMOKE`
- Payload: `{"id":"s-2-3","type":"SMOKE","entrance_num":2,"floor":3,"status":"ALERT"}`
- Запуск: вручную (кнопка)

**inject "Reset 2/5 Water"**
- Тема: `smartresidency/sensors/2/5/WATER`
- Payload: `{"id":"w-2-5","type":"WATER","entrance_num":2,"floor":5,"status":"NORMAL"}`
- Запуск: вручную (кнопка). Сбрасывает датчик обратно в NORMAL

**inject "Heartbeat all 54"**
- Запуск: автоматически каждые **30 секунд** (поле `repeat: "30"`)
- Payload: просто timestamp (дата), это сигнал для function-ноды
- Связан с function-нодой "Build 54 heartbeats"

**function "Build 54 heartbeats"** (JavaScript)
```javascript
const msgs = [];
for (let e = 1; e <= 3; e++) {       // 3 подъезда
    for (let f = 1; f <= 9; f++) {   // 9 этажей
        for (const t of [["w","WATER"],["s","SMOKE"]]) {
            msgs.push({
                topic: `smartresidency/sensors/${e}/${f}/${t[1]}`,
                payload: { id:`${t[0]}-${e}-${f}`, type:t[1],
                           entrance_num:e, floor:f, status:"NORMAL" }
            });
        }
    }
}
return [msgs];  // массив = 54 сообщения за один тик
```
Результат: одна кнопка → 54 MQTT-сообщения, по одному на каждый датчик.

**MQTT-out "Publish Sensor Alert"**
- QoS: 1 (гарантированная доставка)
- Retain: false (сообщение не хранится на брокере)
- Брокер: HiveMQ через конфиг `7b6364188d215929`

**mqtt-broker конфиг "HiveMQ"**
- URL: `e2279f1bd33640749aebe8fb50417c55.s1.eu.hivemq.cloud:8883`
- Port: 8883 (MQTT over TLS, зашифровано)
- TLS: включён, `verifyservercert: true` — проверяем сертификат сервера
- Protocol: MQTT v4 (3.1.1)
- Keepalive: 60 сек — TCP-соединение живёт постоянно

| Файл | Для кого | Содержит | Секрет? |
|---|---|---|---|

### Как бэк отправляет пуш (упрощённо)

3. Шлёт HTTP POST на `fcm.googleapis.com` с токенами устройств и данными
4. Google доставляет пуш на устройство

Всё это под капотом SDK — мы пишем просто `messaging.SendEachForMulticast(...)`.

# ЧАСТЬ 6. GO БЭКЕНД — КАК ВСЁ СВЯЗАНО

## main.go — порядок запуска (можно нарисовать на доске)

```
1. godotenv.Load()          → читаем .env (пароли, ключи)
2. db.Connect()             → подключились к PostgreSQL
3. sensors.Seed()           → создали 54 датчика если их нет
4. fcm.New()                → подключились к Firebase
5. sse.NewHub()             → создали SSE-хаб (комната для слушателей)
6. go sweeper.Run()         → запустили горутину OFFLINE-детектора
7. mqtt.New()               → подключились к HiveMQ, подписались на топики
8. gin router + handlers    → зарегистрировали все API-эндпоинты
9. r.Run(":8080")           → запустили HTTP-сервер
```

Всё это — **один процесс**, параллельно. Go-горутины.

## MQTT топики на которые подписан бэк

```
smartresidency/sensors/+/+/+        ← датчики (+ = wildcard)
smartresidency/events/+             ← события (дублирующий канал)
smartresidency/barrier/camera/plate ← шлагбаум: номер авто с камеры
smartresidency/barrier/motion       ← шлагбаум: датчик движения
smartresidency/parking/spots/+      ← парковка: статус места
```

## Что происходит при получении sensor-сообщения (главный код)

```
MQTT-сообщение пришло
        ↓
1. Распарсили JSON
        ↓
2. SELECT status FROM sensors WHERE id=$1   ← предыдущий статус
        ↓
3. INSERT ON CONFLICT DO UPDATE             ← UPSERT: обновили статус + last_seen_at
        ↓
4. Статус изменился? Если да → hub.Broadcast("sensor_update") → SSE → Админ-Flutter
        ↓
5. Был NORMAL, стал ALERT?
   ДА → INSERT sensor_events (новое событие)
       → hub.Broadcast("event_new") → SSE → Админ
       → go notifier.NotifyEvent() [горутина, не блокирует]
            ↓
         SELECT fcm_tokens WHERE entrance=$1 AND approved
            ↓
         Firebase multicast → пуш на телефоны жителей
```

## Структура таблиц которые задействованы (минимум)

```
sensors          — 54 строки, статус + last_seen_at
sensor_events    — одно событие = одна строка, timeline через 4 колонки дат
fcm_tokens       — токены устройств привязанные к user_id
profiles         — entrance, floor, verification_status, role, specialty
service_requests — заявки: assigned_to (staff ID), taken_at
```

# ЧАСТЬ 7. ЧТО ГОВОРИТЬ НА ТИПИЧНЫЕ ВОПРОСЫ

## «Как работает реалтайм у Admin?»
> «SSE — Server-Sent Events. Один долгоживущий HTTP-запрос от Flutter к бэку. Когда MQTT приносит событие, бэк через hub.Broadcast отправляет фрейм всем подключённым клиентам-слушателям через их Go-каналы. Flutter получает и обновляет UI без перезагрузки.»

## «Как пуш доходит только до жителей нужного подъезда?»
> «При отправке пуша мы делаем SQL JOIN: fcm_tokens JOIN profiles WHERE profiles.entrance = $1 AND verification_status='approved'. То есть отбираем токены только верифицированных жителей именно того подъезда, где сработал датчик. Жители других подъездов ничего не получают.»

## «Зачем heartbeat каждые 30 секунд?»
> «Без heartbeat мы не знаем — датчик молчит потому что всё спокойно, или потому что он сломан. Heartbeat — это «я живой». OFFLINE-sweeper проверяет last_seen_at каждые 15 секунд. Если прошло больше 60 секунд — помечает датчик OFFLINE и шлёт пуш администратору. Это стандартный IoT-паттерн liveness detection.»

## «Почему не хранить пароли в открытом виде?»
> «bcrypt хеширует пароль с автоматической солью. Из хеша нельзя получить пароль обратно — это одностороннее преобразование. При логине мы снова хешируем введённый пароль и сравниваем хеши. Даже если базу украдут — паролей там нет.»

## «Что такое UPSERT и зачем?»
> «INSERT ... ON CONFLICT DO UPDATE. Атомарная операция: если датчик уже есть — обновить, если нет — вставить. Без этого пришлось бы делать SELECT → IF EXISTS → INSERT или UPDATE: два запроса и потенциальный race condition. UPSERT — один атомарный запрос.»

## «Как защищён API?»
> «Три уровня: JWT-токен в каждом запросе (без него 401), проверка роли в каждом handler'е (резидент в admin-раздел → 403), параметризованные SQL-запросы (защита от SQL-инъекции). Плюс резидент видит только события своего подъезда — проверяем entrance в profiles.»

## «Почему нет HTTPS на вашем бэке?»
> «Бэк запускаем локально для демо, поэтому HTTP. В продакшене поставили бы Nginx или Caddy перед бэком — они терминируют TLS, а дальше передают на localhost:8080 уже без шифрования. Это стандартная архитектура: TLS termination at reverse proxy. Сертификат — бесплатно через Let's Encrypt.»

## «Что если сервер упадёт — потеряются события?»
> «MQTT-брокер HiveMQ Cloud не падает — это управляемый сервис. Go-клиент настроен на AutoReconnect и ConnectRetry — при обрыве автоматически переподключится. Данные в PostgreSQL не теряются — транзакции. Retained сообщения на брокере сохраняются.»

## «В чём новшество вашего проекта по сравнению с простым ЖКХ-приложением?»
> «IoT-интеграция — реалтайм мониторинг датчиков через MQTT с автоматическими push-уведомлениями жителям. Плюс: OFFLINE-детекция через heartbeat, адресная доставка по подъездам, SSE для admin без polling. И ролевая система staff с фильтрацией заявок по специализации — это приближает проект к реальному продукту управляющей компании.»

## Как MQTT-подписка устроена в коде

```go
// При подключении к HiveMQ:
client.Subscribe("smartresidency/sensors/+/+/+", 1, s.handleSensor)
// Первый + = любой подъезд (1-3)
// Второй + = любой этаж (1-9)
// Третий + = WATER или SMOKE
// QoS 1 = гарантированная доставка (at least once)
```

## Как SSE-hub рассылает всем Admin-клиентам

```go
// Каждый подключённый Admin имеет свой Go-канал (chan []byte)
// Broadcast кладёт фрейм в каждый канал:
for ch := range h.clients {
    select {
    case ch <- frame:   // доставили
    default:            // канал переполнен — пропускаем (slow client protection)
    }
}
```

## Как работает OFFLINE-sweeper

```go
// Горутина, каждые 15 сек:
UPDATE sensors SET status='OFFLINE', last_updated=NOW()
WHERE status != 'OFFLINE'
  AND last_seen_at < NOW() - make_interval(secs => 60)
RETURNING id, type, entrance_num, floor
// Для каждой строки из RETURNING → FCM пуш Admin + SSE broadcast
```

Один SQL = нашли всех молчащих + пометили. Атомарно.

## Формат MQTT-payload от датчика

```json
{
  "id": "w-2-5",
  "type": "WATER",
  "entrance_num": 2,
  "floor": 5,
  "status": "ALERT"
}
```

Поле `status`: `NORMAL` (всё ок), `ALERT` (тревога), `OFFLINE` (не отвечает)

## Как создаётся sensor event

Событие создаётся ТОЛЬКО при переходе `NORMAL→ALERT` или `OFFLINE→ALERT`.
Если уже `ALERT→ALERT` — дубль, игнорируем.
Если `ALERT→NORMAL` — датчик успокоился, событие не создаём (оно уже есть в БД).

```go
shouldCreateEvent := hadRow && msg.Status == "ALERT" && (prev == "NORMAL" || prev == "OFFLINE")
```

## Timeline события (как строится в БД)

Одно событие в `sensor_events` = 4 nullable timestamp-поля:
- `created_at` — когда создано (= DETECTED)
- `checking_at` — когда Admin нажал «Проверяю»
- `confirmed_at` — когда подтвердил
- `false_alarmed_at` — когда отметил ложную тревогу

Flutter берёт эти поля и рисует timeline с шагами.
