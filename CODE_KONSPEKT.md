# ЧАСТЬ 1. GO ЗА 20 МИНУТ (всё что встретишь в нашем коде)

## 1.1 Пакеты и импорты

```go
package handler          // каждый файл принадлежит пакету (как модуль в JS)

import (
    "net/http"           // стандартная библиотека
    "github.com/gin-gonic/gin"   // внешняя библиотека
    "smartresidency/internal/sse" // наш внутренний пакет
)
```

**Аналогия с JS:** `package` ≈ имя модуля, `import` ≈ `require`/`import`.
Разница: в Go имя пакета — это **папка**. Все файлы в папке `internal/handler/` имеют `package handler`.

## 1.2 Переменные

```go
var x int = 5     // полная форма
x := 5            // короткая форма (Go сам поймёт что это int)
```

`:=` — это «создать новую переменную и присвоить». `=` — «присвоить уже существующей».
**Аналогия:** `:=` ≈ `let x = 5`, `=` ≈ `x = 5`.

## 1.3 Структуры (struct) — это объекты Go

```go
type Sensor struct {
    ID     string
    Status string
    Floor  int
}

s := Sensor{ID: "w-2-5", Status: "NORMAL", Floor: 5}
fmt.Println(s.Status)  // "NORMAL"
```

**Аналогия с JS:** это как объект с заранее объявленными полями и их типами.
В JS: `const s = { id: "w-2-5", status: "NORMAL", floor: 5 }`.
Разница: в Go ты обязан заранее описать, какие поля и какого типа.

### JSON-теги (очень важно — встретишь в каждой структуре)

```go
type Sensor struct {
    ID          string `json:"id"`
    EntranceNum int    `json:"entrance_num"`
}
```

Текст в `` `json:"..."` `` называется **тег**. Он говорит: «когда превращаешь
эту структуру в JSON для отправки в приложение — назови поле `id`, а не `ID`».
В Go поля с большой буквы = публичные, но JSON принято писать с маленькой/со
змейкой (`entrance_num`). Тег связывает одно с другим.

## 1.4 Указатели `*` и `&` (этого в JS нет!)

Это самое непривычное. Разберём медленно.

- `int` — обычное число, например `5`.
- `*int` — «указатель на int», т.е. **адрес в памяти**, где лежит число. Либо число, либо `nil` (пусто).
- `&x` — «взять адрес переменной x».
- `*p` — «прочитать значение по адресу p» (разыменование).

**Зачем это нам?** Главная причина в нашем коде — **различать "ноль" и "не задано"**.

```go
Entrance *int `json:"entrance"`
```

Если `Entrance == nil` — у жителя подъезд **не указан вообще**.
Если `*Entrance == 0` — подъезд указан и равен 0.
С обычным `int` мы бы не отличили «не задано» от «ноль». Поэтому `*int`.

**Аналогия с JS:** `*int` ≈ значение, которое может быть `number` или `null`/`undefined`.
В нашем коде ты увидишь `*string`, `*time.Time`, `*int` — всё это «значение ИЛИ null».

## 1.5 Обработка ошибок: `if err != nil` (вместо try/catch)

В Go нет `try/catch`. Функция, которая может ошибиться, **возвращает ошибку
вторым значением**, и ты обязан её проверить:

```go
hash, err := bcrypt.GenerateFromPassword(...)
if err != nil {
    // что-то пошло не так — обрабатываем и выходим
    return
}
// если дошли сюда — ошибки нет, hash валиден
```

**Аналогия с JS:**
```js
try { const hash = await bcrypt.hash(...) }
catch (err) { ... }
```
В Go это «развёрнуто» в явный возврат и проверку. Поэтому `if err != nil`
встречается в коде сотни раз — это нормально, это стиль языка.

## 1.6 Функции и методы

```go
// обычная функция
func makeToken(userID string) (string, error) { ... }
//              ^параметр       ^возвращает строку И ошибку

// метод (функция, привязанная к структуре)
func (h *AuthHandler) Login(c *gin.Context) { ... }
//    ^"получатель" — на какой структуре вызывается
```

`(h *AuthHandler)` — это **получатель** (receiver). Значит метод `Login`
вызывается так: `authHandler.Login(c)`. Внутри `h` — это сам объект.
**Аналогия с JS:** это как метод класса, где `h` ≈ `this`.

Go может возвращать **несколько значений** — `(string, error)`. В JS пришлось бы
вернуть массив или объект.

## 1.7 Интерфейсы (КЛЮЧЕВАЯ тема — у нас они везде)

Интерфейс — это **список методов**. Любая структура, у которой есть эти методы,
**автоматически** подходит под интерфейс (ничего объявлять не надо).

```go
// "Notifier — это что угодно, что умеет NotifyEvent"
type EventNotifier interface {
    NotifyEvent(ctx context.Context, eventID string) (int, error)
}
```

У нас `*fcm.Sender` имеет метод `NotifyEvent(...)` → значит он автоматически
является `EventNotifier`. Мы можем передать его туда, где ждут `EventNotifier`.

**Зачем нам это?** Чтобы код не зависел жёстко от Firebase. Sensors-handler
знает только «есть некий notifier, умеющий слать пуш». Если завтра заменим
Firebase на что-то другое — handler не изменится. Плюс если FCM выключен,
notifier = `nil`, и сервер всё равно запускается.

**Аналогия с JS:** это «утиная типизация» — «если крякает как утка, значит утка».
В JS ты просто передаёшь объект с нужным методом; в Go это формализовано через `interface`.

## 1.8 Горутины и каналы (ГЛАВНАЯ фишка Go — спросят 100%)

### Горутина — это «запусти эту функцию параллельно»

```go
go notifier.NotifyEvent(ctx, eventID)
```

Слово `go` перед вызовом = «запусти в фоне, не жди результата, продолжай дальше».
**Аналогия с JS:** похоже на запуск async-функции без `await`. Но горутины
гораздо легче: их можно запустить тысячи, Go сам распределит по ядрам процессора.

В нашем коде мы шлём пуш в горутине, чтобы **не блокировать** обработку MQTT-сообщения.
Пуш может идти 1-2 секунды (запрос к Google), а мы не хотим тормозить приём датчиков.

### Канал (chan) — это «труба» для передачи данных между горутинами

```go
ch := make(chan []byte, 16)  // канал на 16 сообщений
ch <- frame                  // положить в канал (отправить)
frame := <-ch                // взять из канала (получить)
```

**Аналогия с JS:** канал — как очередь/стрим. Одна горутина пишет, другая читает.
У нас SSE-хаб использует канал: когда приходит событие от датчика, мы кладём его
в канал, а горутина, обслуживающая Admin-соединение, забирает и шлёт в браузер.

`make(chan []byte, 16)` — «буферизованный» канал на 16 элементов. Если он полон —
запись либо ждёт, либо (у нас) сообщение отбрасывается, чтобы не зависнуть.

### `select` — ждать сразу из нескольких каналов

```go
select {
case <-ctx.Done():        // если соединение закрылось — выходим
    return
case frame := <-ch:       // если пришёл новый фрейм — шлём
    отправить(frame)
case <-ping.C:            // если сработал таймер — шлём ping
    отправить("ping")
}
```

**Аналогия с JS:** как `Promise.race()` — реагируем на то, что случилось первым.

### Мьютекс (sync.Mutex / RWMutex) — защита от гонки

Когда несколько горутин трогают одни данные одновременно — может быть «гонка»
(race condition), данные портятся. Мьютекс — это «замок»: пока одна горутина
держит замок, остальные ждут.

```go
h.mu.Lock()      // взять замок (эксклюзивно)
... меняем данные ...
h.mu.Unlock()    // отпустить

h.mu.RLock()     // взять замок на ЧТЕНИЕ (несколько читателей можно одновременно)
... читаем ...
h.mu.RUnlock()
```

`RWMutex` = Read-Write Mutex: много читателей одновременно ОК, но писатель — один и
блокирует всех. У нас в SSE-хабе: добавление/удаление клиента = запись (Lock),
рассылка сообщения = чтение списка клиентов (RLock).

## 1.9 `defer` — «сделай это при выходе из функции»

```go
rows, err := db.Query(...)
defer rows.Close()   // закрой rows, когда функция завершится (что бы ни случилось)
```

`defer` откладывает выполнение строки до конца функции. Удобно для «закрыть
соединение / отпустить замок» — не забудешь, даже если выйдешь раньше из-за ошибки.
**Аналогия с JS:** как `finally {}`, но привязанное к одной строке.

## 1.10 Слайсы и мапы

```go
var tokens []string              // слайс (динамический массив), как Array в JS
tokens = append(tokens, "abc")   // добавить элемент

byStatus := map[string]int{}     // мапа (словарь), как объект/Map в JS
byStatus["DETECTED"] = 5
```

`[]string` ≈ массив строк. `map[string]int` ≈ объект, где ключ — строка, значение — число.

## 1.11 `context.Context` (ctx) — встречается в КАЖДОЙ функции, обязательно пойми

В нашем коде почти каждая функция принимает `ctx context.Context` первым аргументом,
и ты увидишь `context.Background()`, `c.Request.Context()`, `ctx.Done()`. Что это?

**Контекст — это «конверт управления запросом».** Он несёт две вещи:
1. **Сигнал отмены** — «запрос больше не нужен, прекращай работу». Например, если
   пользователь закрыл соединение или вышло время — все операции с этим `ctx`
   (запросы к БД, ожидание в `select`) могут досрочно прерваться. Это экономит ресурсы.
2. **Срок/дедлайн** — можно сказать «эта операция должна уложиться в N секунд».

**Аналогия с JS:** это как `AbortController`/`AbortSignal` — объект, через который
можно отменить «висящую» операцию.

Где что в нашем коде:
- `context.Background()` — «пустой корневой контекст», когда отменять нечего
  (например в фоновой горутине пуша). Это «заглушка-родитель».
- `c.Request.Context()` — контекст конкретного HTTP-запроса. Когда клиент отключился,
  этот контекст «закрывается».
- `<-ctx.Done()` — в `select` означает «сработал сигнал отмены» (см. SSE Stream и sweeper).

Тебе НЕ нужно создавать контексты вручную — ты просто **прокидываешь** `ctx` дальше
в вызовы БД. Это стандарт Go: «отмена должна пробрасываться по цепочке вызовов».

## 1.12 `gin.Context` (c) и `gin.H` — в каждом handler'е

```go
func (h *AuthHandler) Login(c *gin.Context) { ... }
```

`c *gin.Context` — это **главный объект запроса в Gin**. В нём одновременно:
- **входящие данные**: тело запроса (`c.ShouldBindJSON`), параметры пути
  (`c.Param("id")`), query-параметры (`c.Query("entrance")`), заголовки (`c.GetHeader`).
- **выходные данные**: ответ клиенту (`c.JSON(200, ...)`).
- **общая память запроса**: `c.Set("user_id", ...)` / `c.GetString("user_id")` —
  так middleware передаёт данные в handler.

**Аналогия с JS/Express:** `c` ≈ `req` и `res`, склеенные в один объект.

```go
c.JSON(http.StatusOK, gin.H{"token": token, "user_id": userID})
```

`gin.H` — это просто **сокращение для `map[string]any`** (словарь строка→что угодно).
Удобный способ собрать JSON-ответ на лету. `gin.H{"error": "..."}` → `{"error":"..."}`.

## 1.13 `_` — пустой идентификатор («мне это значение не нужно»)

Ты увидишь `_` повсюду. Это «мусорка»: «функция что-то вернула, но мне не нужно».

```go
_ = godotenv.Load()        // функция вернула ошибку, но мы её игнорируем
_, err := h.db.Exec(...)   // первое значение (результат) не нужно, нужна только ошибка
func (s *Subscriber) handleSensor(_ paho.Client, m paho.Message) // первый аргумент не используем
```

**Зачем?** В Go нельзя объявить переменную и не использовать её — будет ошибка
компиляции. `_` говорит компилятору «я осознанно выбрасываю это значение». Это не
лень, а явное намерение.

## 1.14 `any` (он же `interface{}`) — «значение любого типа»

```go
func (h *Hub) Broadcast(event string, data any) error
args := []any{}
map[string]any{ "id": msg.ID, "floor": msg.Floor }
```

`any` = «что угодно» (число, строка, структура — любой тип). Используем там, где
данные заранее неизвестны: например в JSON-ответе значения бывают разных типов.
**Аналогия с JS:** в JS все переменные и так «any», там это норма. В Go это
отдельный тип, который применяют осознанно, когда тип не зафиксирован.

## 1.15 HTTP-коды ответов (используются везде в `c.JSON`)

В handler'ах ты увидишь `http.StatusOK` и числа. Что они значат:

| Код | Константа Go | Когда мы возвращаем |
|---|---|---|
| 200 | `StatusOK` | успех (GET, обновление) |
| 201 | `StatusCreated` | успешно создано (регистрация, новая заявка) |
| 204 | `StatusNoContent` | успех без тела (ответ на OPTIONS/CORS) |
| 400 | `StatusBadRequest` | плохой ввод (не прошла валидация) |
| 401 | `StatusUnauthorized` | нет/невалидный токен (ловит middleware) |
| 403 | `StatusForbidden` | токен есть, но роль не та (не админ лезет в admin) |
| 404 | `StatusNotFound` | не нашли (нет такого события/датчика) |
| 409 | `StatusConflict` | конфликт (email занят, бронь пересекается) |
| 500 | `StatusInternalServerError` | ошибка на сервере (логируем, клиенту общий текст) |

**Правило, которое мы соблюдаем:** клиенту 4xx — «ты сделал не так», 5xx — «у нас
сломалось». При 500 мы не светим детали наружу (см. `internalError` в `log.go`).

# ЧАСТЬ 1-БИС. ПУТЬ ОДНОГО ЗАПРОСА (всё вместе на одном примере)

Прежде чем нырять в файлы — проследим **один реальный запрос от начала до конца**.
Это свяжет все понятия. Пример: житель открыл приложение, оно запрашивает датчики
своего подъезда — `GET /api/v1/sensors?entrance=2` с токеном в заголовке.

```
1. Flutter шлёт:  GET /api/v1/sensors?entrance=2
                  Header: Authorization: Bearer eyJhbGc...   (JWT-токен)
        │
        ▼
2. Gin принимает запрос. Путь /api/v1/sensors лежит в группе priv,
   на которой висит middleware.Auth (см. main.go:132).
        │
        ▼
3. middleware/auth.go выполняется ПЕРЕД handler'ом:
   - достаёт токен из заголовка
   - проверяет подпись секретом JWT_SECRET и срок
   - НЕвалиден → c.AbortWithStatusJSON(401) — handler НЕ вызовется, конец.
   - валиден → c.Set("user_id", ...), c.Set("user_role", ...) и c.Next()
        │
        ▼
4. Вызывается handler SensorHandler.ListByEntrance (sensors.go:100):
   - читает entrance из query: c.Query("entrance") → "2"
   - делает SQL: SELECT ... FROM sensors WHERE entrance_num=$1  (параметр $1 = 2)
   - pgx возвращает строки, scanSensors превращает их в []Sensor
        │
        ▼
5. handler отвечает: c.JSON(200, out)  → Gin сериализует []Sensor в JSON
        │
        ▼
6. Flutter получает JSON-массив датчиков и рисует сетку.
```

**Что здесь видно (повтори это себе):**
- **два слоя защиты:** сначала middleware (есть ли валидный токен → 401), потом сам
  handler (роль/подъезд).
- **данные из токена, а не от клиента:** `user_id` берётся из проверенного JWT, ему
  можно доверять. Клиент не может притвориться другим.
- **параметризованный SQL `$1`** — клиентский `entrance` не склеивается в строку.
- Весь путь — синхронный и быстрый. А вот пуши/тяжёлое — уходят в горутины (см. дальше).

Держи эту схему в голове — все handler'ы работают по ней.

## Блок 3 — Firebase (строки 49–68)


Тут важная идея. Мы создаём **один** объект `fcm.Sender` (`s`), и присваиваем его

## Блок 8 — регистрация маршрутов (строки 124–220)

```go

api.POST("/auth/register", authH.Register)
api.POST("/auth/login", authH.Login)

// ЗАЩИЩЁННЫЕ — требуют JWT
```

- `priv` (защищённый) — `priv.Use(middleware.Auth(secret))` вешает на ВСЕ маршруты

# ЧАСТЬ 4. ГЛУБОКО: MQTT-ПОДПИСЧИК (`internal/mqtt/client.go`)

Это сердце IoT. Сюда приходят сообщения от датчиков. Разберём максимально подробно.

## 4.1 Что такое MQTT (напомни себе перед объяснением кода)

MQTT — протокол «publish/subscribe» (издатель/подписчик). Есть **брокер** (HiveMQ).
Датчики **публикуют** сообщения в «топики» (как адреса/каналы). Наш бэк **подписан**
на топики и получает все сообщения. Брокер — посредник, датчики и бэк не знают
друг о друге напрямую.

Топик у нас: `smartresidency/sensors/2/5/WATER` = подъезд 2, этаж 5, тип WATER.

## 4.2 Интерфейсы вверху файла (строки 14–24)

```go
type Notifier interface {
    NotifyEvent(ctx context.Context, eventID string) (int, error)
}
type Broadcaster interface {
    Broadcast(event string, data any) error
}
type ParkingNotifier interface {
    SendToUser(ctx context.Context, userID string, data map[string]string) (int, error)
}
```

MQTT-пакет **не знает** про Firebase и SSE напрямую. Он знает только «есть нечто,
умеющее `NotifyEvent`» (Notifier) и «нечто, умеющее `Broadcast`» (Broadcaster).
Реальные объекты (`fcm.Sender`, `sse.Hub`) подставляются снаружи в `main.go`.
Это и есть слабая связанность через интерфейсы.

## 4.3 Структура Subscriber (строки 33–40)

```go
type Subscriber struct {
    db              *pgxpool.Pool   // доступ к БД
    notifier        Notifier        // для пушей
    bcast           Broadcaster     // для SSE
    parkingNotifier ParkingNotifier
    client          paho.Client     // сам MQTT-клиент (библиотека paho)
    barrierCallback func(...)        // функция обработки шлагбаума
}
```

Это «контейнер» со всеми зависимостями. `paho` — название MQTT-библиотеки
(Eclipse Paho, индустриальный стандарт).

## 4.4 Подключение и настройки (функция New, строки 42–102)

```go
opts := paho.NewClientOptions()
opts.AddBroker(cfg.URL)              // адрес HiveMQ
opts.SetUsername(cfg.Username)       // логин backendTest
opts.SetPassword(cfg.Password)       // пароль
opts.SetAutoReconnect(true)          // ← переподключаться при обрыве
opts.SetConnectRetry(true)           // ← повторять попытки подключения
opts.SetCleanSession(true)
opts.SetTLSConfig(&tls.Config{MinVersion: tls.VersionTLS12})  // ← TLS-шифрование
```

**Что объяснять комиссии по каждой настройке:**
- `AutoReconnect(true)` — если связь с брокером порвётся, клиент сам переподключится.
  Это ответ на вопрос «а если интернет пропадёт?».
- `ConnectRetry(true)` — если при старте брокер недоступен, бэк не падает, а повторяет.
- `TLS VersionTLS12` — шифрование канала. Минимум TLS 1.2 (старые версии запрещены).
  Поэтому порт 8883, а не 1883.
- `CleanSession(true)` — не хранить состояние подписки между сессиями (нам не нужно,
  Node-RED шлёт heartbeat заново).

```go
opts.SetOnConnectHandler(func(c paho.Client) {
    c.Subscribe("smartresidency/sensors/+/+/+", 1, s.handleSensor)
    ...
})
```

`SetOnConnectHandler` — функция, которая выполнится **в момент подключения**
(и при каждом переподключении!). Внутри — подписки на топики.

**Почему подписка внутри OnConnect, а не один раз?** Потому что при переподключении
подписки сбрасываются, и их надо восстановить. Поэтому подписываемся в обработчике
подключения — он сработает снова после reconnect.

### Wildcards в топиках (важно объяснить)

```go
c.Subscribe("smartresidency/sensors/+/+/+", 1, s.handleSensor)
```

`+` — это **wildcard** (подстановка одного уровня). `sensors/+/+/+` ловит ВСЕ датчики:
`sensors/2/5/WATER`, `sensors/1/3/SMOKE` и т.д. Не надо подписываться на каждый из 54.

Второй аргумент `1` — это **QoS 1** (Quality of Service). Уровни:
- QoS 0 — «отправил и забыл», доставка не гарантирована
- QoS 1 — «хотя бы один раз» (at least once), гарантированная доставка с подтверждением
- QoS 2 — «ровно один раз», самый надёжный но медленный

Мы выбрали QoS 1: тревога не должна потеряться, а возможный дубль мы отсекаем в коде.

Третий аргумент `s.handleSensor` — функция-обработчик: её вызовут на каждое сообщение.

```go
s.client = paho.NewClient(opts)
if t := s.client.Connect(); t.Wait() && t.Error() != nil {
    return nil, t.Error()
}
```

Создаём клиента и подключаемся. `t.Wait()` блокирует, пока подключение не завершится.
В paho почти все операции возвращают «токен» (token) — объект, у которого можно
дождаться результата через `.Wait()` и проверить `.Error()`.

## 4.5 handleSensor — ГЛАВНАЯ ФУНКЦИЯ (строки 120–203)

Это код, который выполняется на КАЖДОЕ сообщение датчика. Разбираем по шагам.

### Шаг 1 — парсинг JSON (строки 120–130)

```go
func (s *Subscriber) handleSensor(_ paho.Client, m paho.Message) {
    var msg sensorMsg
    if err := json.Unmarshal(m.Payload(), &msg); err != nil {
        return  // битый JSON — игнорируем
    }
    if msg.ID == "" || msg.Status == "" {
        return  // нет обязательных полей — игнорируем
    }
```

`json.Unmarshal(данные, &msg)` — разобрать JSON в структуру `sensorMsg`.
`&msg` — передаём адрес (указатель), чтобы функция заполнила нашу переменную.
**Аналогия с JS:** `const msg = JSON.parse(payload)`.

`sensorMsg` определён выше (строки 104–110) с JSON-тегами: `id`, `type`,
`entrance_num`, `floor`, `status`.

### Шаг 2 — узнаём предыдущий статус (строки 133–134)

```go
var prev string
hadRow := s.db.QueryRow(ctx, `SELECT status FROM sensors WHERE id=$1`, msg.ID).Scan(&prev) == nil
```

Спрашиваем БД: какой статус был у этого датчика раньше? `hadRow` = `true`, если
датчик уже есть в базе (запрос не дал ошибки). `prev` = старый статус.

**Зачем?** Чтобы понять, **изменился ли статус** (для SSE) и **надо ли создавать
событие** (NORMAL→ALERT). Без знания предыдущего статуса мы бы не отличили новую
тревогу от повторного сообщения.

Обрати внимание на `$1` — это **параметр запроса**. Значение `msg.ID` подставляется
безопасно драйвером. Это **защита от SQL-инъекций** (мы НЕ склеиваем строки!).

### Шаг 3 — UPSERT (строки 138–146) — частый вопрос

```go
s.db.Exec(ctx, `
    INSERT INTO sensors (id, type, entrance_num, floor, status, last_updated, last_seen_at)
    VALUES ($1, $2, $3, $4, $5, NOW(), NOW())
    ON CONFLICT (id) DO UPDATE
    SET status = EXCLUDED.status, last_updated = NOW(), last_seen_at = NOW()`,
    msg.ID, msg.Type, msg.EntranceNum, msg.Floor, msg.Status)
```

**UPSERT = INSERT или UPDATE одной командой.** Логика: «вставь датчик; но если
датчик с таким `id` уже есть (`ON CONFLICT (id)`) — вместо вставки обнови ему
статус и временные метки». `EXCLUDED.status` — это значение, которое мы пытались
вставить (новый статус).

**Зачем UPSERT, а не SELECT + IF + INSERT/UPDATE?**
1. **Атомарность** — одна операция, нет «гонки» между проверкой и записью.
2. **Производительность** — один запрос вместо двух-трёх.

**КЛЮЧЕВАЯ деталь — `last_seen_at = NOW()` на КАЖДОЕ сообщение** (даже heartbeat).
Это «отметка живости». Sweeper потом смотрит на неё, чтобы понять — датчик жив или замолчал.

### Шаг 4 — SSE-рассылка при смене статуса (строки 154–162)

```go
if s.bcast != nil && (!hadRow || prev != msg.Status) {
    s.bcast.Broadcast("sensor_update", map[string]any{
        "id": msg.ID, "status": msg.Status, ...
    })
}
```

Условие `prev != msg.Status` = «статус изменился». **Только тогда** шлём обновление
в SSE админам.

**Почему не на каждое сообщение?** Heartbeat приходит 54 раза каждые 30 секунд,
со статусом NORMAL. Если бы мы слали SSE на каждый heartbeat — забили бы канал
54 фреймами каждые 30 сек впустую. А так — шлём только реальные изменения. Это
важная оптимизация, обязательно упомяни.

### Шаг 5 — создание события и пуш (строки 164–202) — САМОЕ ВАЖНОЕ

```go
shouldCreateEvent := hadRow && msg.Status == "ALERT" && (prev == "NORMAL" || prev == "OFFLINE")
```

Событие создаётся **только при переходе в ALERT из спокойного состояния**.
Таблица переходов (она в комментарии в коде, строки 164–170):

| Было → Стало | Действие |
|---|---|
| NORMAL → ALERT | **создать событие + пуш жителям** (тревога!) |
| OFFLINE → ALERT | **создать событие + пуш** (датчик вернулся уже в тревоге) |
| OFFLINE → NORMAL | тихое восстановление, ничего |
| NORMAL → NORMAL | heartbeat, только обновили last_seen_at |
| ALERT → NORMAL | сброс/успокоился, без пуша |
| ALERT → ALERT | дубликат, игнорируем |

Это защищает от **спама**: если датчик 10 раз пришлёт ALERT подряд — событие
создастся один раз (при первом переходе), не 10.

```go
err := s.db.QueryRow(ctx, `
    INSERT INTO sensor_events (id, sensor_id, type, entrance_num, floor, status)
    VALUES ('evt-' || nextval('sensor_events_seq'), $1, $2, $3, $4, 'DETECTED')
    RETURNING id`,
    msg.ID, msg.Type, msg.EntranceNum, msg.Floor).Scan(&eventID)
```

Создаём событие. `'evt-' || nextval('sensor_events_seq')` — генерируем ID типа
`evt-1`, `evt-2`... через PostgreSQL-последовательность (sequence). `RETURNING id` —
вернуть сгенерированный ID сразу (чтобы дальше слать пуш по нему).

```go
if s.bcast != nil {
    s.bcast.Broadcast("event_new", map[string]any{ "id": eventID, ... })
}
if s.notifier != nil {
    go func(id string) {
        s.notifier.NotifyEvent(context.Background(), id)
    }(eventID)
}
```

1. Шлём SSE `event_new` админам (новая тревога в списке — мгновенно).
2. **`go func(...)`** — запускаем отправку пуша **в горутине** (в фоне).

**Почему в горутине?** Отправка пуша через Firebase идёт по сети, может занять
1-2 секунды. Мы НЕ хотим держать обработку MQTT-сообщения всё это время. Запустили
в фоне — и сразу свободны принимать следующее сообщение. Это и есть преимущество Go.

Обрати внимание: `go func(id string){...}(eventID)` — мы передаём `eventID` как
параметр `id`. Это важный паттерн Go: так мы «фиксируем» текущее значение, чтобы
горутина работала именно с ним (а не с изменившейся переменной).

## 4.6 Publish и PublishRetain (строки 413–430)

```go
func (s *Subscriber) Publish(topic, payload string) error {
    t := s.client.Publish(topic, 1, false, payload)  // QoS 1, retain=false
    t.Wait()
    return t.Error()
}

func (s *Subscriber) PublishRetain(topic string, payload any) error {
    data, _ := json.Marshal(payload)
    t := s.client.Publish(topic, 1, true, data)       // retain=TRUE
    t.Wait()
    return t.Error()
}
```

Бэк умеет не только слушать, но и **публиковать**. Используется для:
- открытия шлагбаума (`Publish` команды)
- сброса датчика (`PublishRetain` со статусом NORMAL)

**`retain=true` — частый вопрос.** Retain означает «брокер запомнит последнее
сообщение в этом топике». Когда кто-то подпишется позже — сразу получит последнее
состояние. Для сброса датчика это важно: даже после рестарта бэк/брокер видит, что
датчик в NORMAL. Для обычных сообщений retain=false (не засорять брокер).

# ЧАСТЬ 5. ГЛУБОКО: SSE-ХАБ (`internal/sse/hub.go`)

Всего 70 строк, но концептуально важно. Комиссия любит спрашивать про реалтайм.

## 5.1 Что такое SSE (объясни своими словами)

SSE = Server-Sent Events. Это способ серверу **проталкивать** данные клиенту по
одному долгоживущему HTTP-соединению. Клиент (Flutter-админка) открывает соединение
один раз, и сервер шлёт в него события по мере появления. Клиент не опрашивает
сервер (no polling) — сервер сам уведомляет.

**SSE vs WebSocket:** SSE — односторонний (только сервер→клиент), работает поверх
обычного HTTP, клиент сам переподключается при обрыве. WebSocket — двусторонний,
сложнее. Нам нужно только сервер→клиент (обновления сетки датчиков) → выбрали SSE.

## 5.2 Структура Hub (строки 13–21)

```go
type Hub struct {
    mu      sync.RWMutex
    clients map[chan []byte]struct{}
}
```

`clients` — это **множество каналов**. Каждый подключённый админ = один канал.
`map[chan []byte]struct{}` — это «множество» (set): ключ — канал, значение —
`struct{}{}` (пустая структура, занимает 0 байт, используется как «галочка наличия»).

`mu sync.RWMutex` — замок для защиты `clients`, т.к. к нему обращаются разные горутины.

## 5.3 Subscribe — подключение клиента (строки 26–32)

```go
func (h *Hub) Subscribe() chan []byte {
    ch := make(chan []byte, 16)   // буфер на 16 фреймов
    h.mu.Lock()
    h.clients[ch] = struct{}{}    // добавили канал в множество
    h.mu.Unlock()
    return ch
}
```

Создаём канал на 16 сообщений, добавляем в множество клиентов под замком, возвращаем.
Этот канал отдадут горутине, обслуживающей конкретного админа.

**Почему буфер 16?** Чтобы при коротком всплеске событий медленный клиент не
блокировал отправителя. Если придёт 17-е сообщение, а клиент не успел разобрать —
оно отбросится (см. ниже).

## 5.4 Broadcast — рассылка всем (строки 47–63) — ГЛАВНОЕ

```go
func (h *Hub) Broadcast(event string, data any) error {
    payload, err := json.Marshal(data)
    if err != nil { return err }
    frame := []byte(fmt.Sprintf("event: %s\ndata: %s\n\n", event, payload))
    h.mu.RLock()
    for ch := range h.clients {
        select {
        case ch <- frame:    // успешно положили в канал клиента
        default:             // канал переполнен — ДРОПАЕМ фрейм для этого клиента
        }
    }
    h.mu.RUnlock()
    return nil
}
```

Разбор:
1. `json.Marshal(data)` — превращаем данные в JSON.
2. `frame := ... "event: %s\ndata: %s\n\n"` — формируем **SSE-фрейм**. Это
   текстовый формат SSE: строка `event:` (тип события), строка `data:` (JSON),
   и пустая строка-разделитель `\n\n`. Браузер/Flutter понимают этот формат нативно.
3. `h.mu.RLock()` — берём замок на ЧТЕНИЕ (рассылка читает список клиентов;
   несколько Broadcast могут идти параллельно, но не одновременно с добавлением клиента).
4. Цикл по всем клиентам с `select`:
   - `case ch <- frame:` — пытаемся положить фрейм в канал клиента.
   - `default:` — если канал полон (медленный клиент), мы **не ждём**, а пропускаем
     фрейм для него.

**Это самая важная идея (защита медленного клиента, обязательно объясни):**
> «Один медленный или зависший админ-клиент не должен тормозить рассылку всем
> остальным. Поэтому `select` с `default`: если канал клиента переполнен, мы
> отбрасываем фрейм именно для него и идём дальше. Отправитель никогда не блокируется.»

## 5.5 Кто вызывает Broadcast?

**Один хаб, три источника** (это передаётся в `main.go`):
1. `mqtt.Subscriber` — шлёт `sensor_update`, `event_new` при сообщениях датчиков.
2. `sensors.OfflineSweeper` — шлёт `sensor_offline` когда датчик замолчал.
3. `handler.SensorHandler` — шлёт `event_status` когда админ обработал событие.

Все три держат ссылку на один и тот же `hub` и зовут `hub.Broadcast(...)`.
А приёмная сторона — `Stream` handler (Часть 9) — отдаёт фреймы в HTTP-соединение.

# ЧАСТЬ 6. ГЛУБОКО: OFFLINE-SWEEPER (`internal/sensors/sweeper.go`)

«Sweeper» = «уборщик/обходчик». Фоновая горутина, которая ищет замолчавшие датчики.

## 6.1 Зачем нужен (объясни проблему)

Датчик может сломаться или потерять связь. Тогда он просто **молчит**. Но молчание
само по себе не приходит как сообщение — нет события «я отключился». Значит надо
**активно проверять**: «от кого давно не было вестей?». Это паттерн **liveness
detection** (определение живости) — стандарт в IoT.

Логика: каждый датчик шлёт heartbeat каждые 30 сек → `last_seen_at` обновляется.
Если `last_seen_at` старше 60 секунд → датчик считается OFFLINE.

## 6.2 Структура и конструктор (строки 26–42)

```go
type OfflineSweeper struct {
    db           *pgxpool.Pool
    notifier     OfflineNotifier
    bcast        Broadcaster
    OfflineAfter time.Duration  // 60 секунд — порог "офлайна"
    Interval     time.Duration  // 15 секунд — как часто проверять
}

func NewOfflineSweeper(...) *OfflineSweeper {
    return &OfflineSweeper{ ..., OfflineAfter: 60*time.Second, Interval: 15*time.Second }
}
```

**Числа, которые надо знать:** порог 60 сек, интервал проверки 15 сек, heartbeat 30 сек.
Почему 60, если heartbeat 30? Запас: даже если один heartbeat потеряется (на 30-й сек),
датчик ещё не считается мёртвым. Только пропуск двух heartbeat подряд (>60 сек) → OFFLINE.

## 6.3 Run — главный цикл (строки 45–58)

```go
func (s *OfflineSweeper) Run(ctx context.Context) {
    t := time.NewTicker(s.Interval)   // тикает каждые 15 сек
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():       // сервер выключается — выходим
            return
        case <-t.C:              // сработал тик — проверяем датчики
            s.sweepOnce(ctx)
        }
    }
}
```

`time.NewTicker(15с)` — таймер, который «тикает» в канал `t.C` каждые 15 секунд.
`for { select {...} }` — бесконечный цикл: либо приходит сигнал завершения
(`ctx.Done()`), либо тик (`t.C`) → запускаем одну проверку.

Запускается это из `main.go` так: `go sweeper.Run(ctx)` — то есть в своей горутине,
параллельно всему остальному.

## 6.4 sweepOnce — одна проверка (строки 60–112) — ключевой SQL

```go
rows, err := s.db.Query(ctx, `
    UPDATE sensors
    SET status = 'OFFLINE', last_updated = NOW()
    WHERE status != 'OFFLINE'
      AND last_seen_at < NOW() - make_interval(secs => $1)
    RETURNING id, type, entrance_num, floor`,
    int(s.OfflineAfter.Seconds()))
```

**Один SQL делает всё.** Разбор:
- `WHERE status != 'OFFLINE'` — не трогаем тех, кто уже офлайн (чтобы не слать пуш повторно).
- `AND last_seen_at < NOW() - 60 секунд` — отбираем тех, от кого нет вестей > 60 сек.
- `SET status = 'OFFLINE'` — помечаем их офлайн.
- `RETURNING id, type, ...` — возвращаем список тех, кого только что пометили.

**Гениальность:** «найти всех замолчавших И пометить их» — это **одна атомарная
операция**. Условие `status != 'OFFLINE'` гарантирует, что каждый датчик
объявляется офлайн **ровно один раз** за один период недоступности (не спамим).

```go
for _, o := range batch {
    if s.bcast != nil {
        s.bcast.Broadcast("sensor_offline", map[string]any{...})  // SSE админу
    }
    go func(o offline) {
        s.notifier.NotifyOffline(ctx, o.id, o.typ, o.entrance, o.fl)  // пуш админу
    }(o)
}
```

Для каждого новоофлайненного датчика: шлём SSE-событие `sensor_offline` админам
и пуш через FCM (в горутине, чтобы не блокировать).

**Что сказать комиссии:**
> «Sweeper — это фоновая горутина, реализующая liveness detection. Каждые 15 секунд
> одним атомарным UPDATE с RETURNING она находит датчики, молчавшие больше 60 секунд,
> помечает их OFFLINE и уведомляет администратора. Условие status != OFFLINE
> гарантирует ровно одно уведомление за период недоступности.»

# ЧАСТЬ 8. АВТОРИЗАЦИЯ: JWT + bcrypt

Два файла: `internal/handler/auth.go` (регистрация/логин) и
`internal/middleware/auth.go` (проверка токена на каждом запросе).

## 8.1 Регистрация (auth.go, строки 40–92)

```go
hash, err := bcrypt.GenerateFromPassword([]byte(req.Password), bcrypt.DefaultCost)
```

**bcrypt — хеширование пароля.** Мы НЕ храним пароль. Храним необратимый хеш.
`bcrypt.DefaultCost` — «стоимость» (сколько раундов хеширования, по умолчанию 10).
Чем больше — тем дольше подбирать перебором. bcrypt автоматически добавляет «соль»
(случайные данные), поэтому два одинаковых пароля дают разные хеши.

```go
h.db.Exec(ctx, `INSERT INTO users (id, email, password_hash) VALUES ($1, $2, $3)`,
    userID, strings.ToLower(strings.TrimSpace(req.Email)), string(hash))
```

Создаём пользователя. Email приводим к нижнему регистру и обрезаем пробелы
(`ToLower` + `TrimSpace`) — чтобы `Ivan@x.ru` и `ivan@x.ru ` были одним аккаунтом.

```go
if strings.Contains(err.Error(), "23505") || strings.Contains(err.Error(), "duplicate") {
    c.JSON(http.StatusConflict, gin.H{"error": "email already registered"})
}
```

`23505` — код ошибки PostgreSQL «нарушение уникальности» (email уже занят).
Ловим его и возвращаем понятный 409 Conflict вместо 500.

Дальше создаётся профиль (роль `resident`, статус `not_submitted`) и выдаётся токен.

## 8.2 Логин (auth.go, строки 99–132)

```go
err := h.db.QueryRow(ctx, `
    SELECT u.id, u.password_hash, COALESCE(p.role, 'resident')
    FROM users u LEFT JOIN profiles p ON p.id = u.id
    WHERE u.email = $1`, ...).Scan(&userID, &hash, &role)
if err != nil {
    c.JSON(http.StatusUnauthorized, gin.H{"error": "invalid credentials"})
}

if err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(req.Password)); err != nil {
    c.JSON(http.StatusUnauthorized, gin.H{"error": "invalid credentials"})
}
```

1. Достаём из БД хеш пароля и роль по email. `COALESCE(p.role, 'resident')` —
   если роль не задана, считаем `resident`.
2. `bcrypt.CompareHashAndPassword` — bcrypt сам хеширует введённый пароль с той же
   солью и сравнивает с хранимым хешем. Мы **никогда не расшифровываем** хеш.

**Деталь безопасности:** при неверном email И при неверном пароле возвращаем
**одинаковую** ошибку «invalid credentials». Чтобы злоумышленник не понял, какой
именно email существует в системе (защита от перебора аккаунтов).

## 8.3 Генерация JWT (auth.go, строки 172–184)

```go
func makeToken(userID, email, role string) (string, error) {
    claims := middleware.Claims{
        UserID: userID, Email: email, Role: role,
        RegisteredClaims: jwt.RegisteredClaims{
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(24 * time.Hour)),
            IssuedAt:  jwt.NewNumericDate(time.Now()),
        },
    }
    t := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return t.SignedString([]byte(os.Getenv("JWT_SECRET")))
}
```

**JWT = JSON Web Token.** Это «пропуск», который сервер выдаёт после логина.
Внутри (claims) — `user_id`, `email`, `role`, срок жизни (24 часа).
`SigningMethodHS256` — алгоритм подписи. Токен **подписывается** секретом
`JWT_SECRET`. Подпись гарантирует: токен не подделать, не зная секрет.

**Что объяснять про JWT:**
> «JWT состоит из трёх частей: header, payload (наши данные — id, роль, срок) и
> подпись. Подпись = хеш от header+payload+секрет. Клиент хранит токен и шлёт его в
> каждом запросе. Сервер проверяет подпись своим секретом — если совпала, токену
> можно верить, не обращаясь к БД. Это stateless-авторизация: серверу не надо хранить
> сессии. Срок 24 часа — потом нужен refresh.»

## 8.4 Middleware проверки (middleware/auth.go) — на каждом запросе

```go
func Auth(secret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        raw := ""
        if h := c.GetHeader("Authorization"); strings.HasPrefix(h, "Bearer ") {
            raw = strings.TrimPrefix(h, "Bearer ")
        } else if q := c.Query("token"); q != "" {
            raw = q    // ← токен из query-параметра (для SSE!)
        }
        if raw == "" {
            c.AbortWithStatusJSON(401, gin.H{"error": "missing token"})
            return
        }
        token, err := jwt.ParseWithClaims(raw, &Claims{},
            func(t *jwt.Token) (any, error) { return []byte(secret), nil })
        if err != nil || !token.Valid {
            c.AbortWithStatusJSON(401, gin.H{"error": "invalid token"})
            return
        }
        claims := token.Claims.(*Claims)
        c.Set("user_id", claims.UserID)
        c.Set("user_role", claims.Role)
        c.Next()
    }
}
```

Это **middleware** — функция, выполняемая ПЕРЕД handler'ом на защищённых маршрутах.
1. Достаёт токен из заголовка `Authorization: Bearer <токен>`.
2. **Особый случай для SSE:** EventSource (стандарт SSE в браузере) не умеет слать
   заголовки. Поэтому для `/stream` токен принимается из query: `?token=<JWT>`.
   Это объясняет строку `else if q := c.Query("token")`.
3. `jwt.ParseWithClaims` — проверяет подпись и срок. Если невалиден → 401, `Abort`
   (запрос не дойдёт до handler'а).
4. Если валиден — кладёт `user_id` и `user_role` в контекст (`c.Set`). Дальше любой
   handler берёт их через `c.GetString("user_id")`. Это связь между middleware и handler'ами.

**Это ответ на «как защищён API»:** каждый защищённый запрос проходит через `Auth`,
без валидного токена — 401, не дойдя до бизнес-логики.

## 9.5 Stream — это и есть SSE-сервер (строки 274–323) — ВАЖНО

```go
c.Writer.Header().Set("Content-Type", "text/event-stream")
c.Writer.Header().Set("Cache-Control", "no-cache")
c.Writer.Header().Set("Connection", "keep-alive")
c.Writer.Header().Set("X-Accel-Buffering", "no")

flusher, ok := c.Writer.(http.Flusher)

ch := h.hub.Subscribe()
defer h.hub.Unsubscribe(ch)

io.WriteString(c.Writer, ":connected\n\n")
flusher.Flush()
```

Это **приёмная сторона SSE** (хаб из Части 5 — отправная). Разбор:
- `Content-Type: text/event-stream` — говорит клиенту «это SSE-поток».
- `flusher` — нужен чтобы **проталкивать** данные сразу, не буферизуя.
- `h.hub.Subscribe()` — регистрируемся в хабе, получаем свой канал.
- `defer Unsubscribe` — при закрытии соединения отписываемся (важно, иначе утечка).
- `:connected\n\n` — комментарий-приветствие (строка с `:` в SSE = комментарий).

```go
ping := time.NewTicker(15 * time.Second)
for {
    select {
    case <-c.Request.Context().Done():   // клиент отключился
        return
    case frame, ok := <-ch:               // пришёл фрейм из хаба
        c.Writer.Write(frame)
        flusher.Flush()
    case <-ping.C:                         // каждые 15 сек — keepalive
        io.WriteString(c.Writer, ":ping\n\n")
        flusher.Flush()
    }
}
```

Вечный цикл с `select` на три случая:
1. Соединение закрылось → выходим (и срабатывает `defer Unsubscribe`).
2. Из канала пришёл фрейм (кто-то вызвал `hub.Broadcast`) → пишем клиенту + flush.
3. Таймер ping каждые 15 сек → шлём `:ping` (keepalive, чтобы прокси/мобильная сеть
   не закрыли «молчащее» соединение).

**Это полная картина SSE:** MQTT/sweeper зовёт `hub.Broadcast` → хаб кладёт фрейм в
канал → эта горутина (`Stream`) забирает из канала → пишет в HTTP-соединение → Flutter.

## 9.6 Stats — агрегаты для дашборда (строки 486–583)

## 10.2 List — фильтрация заявок по роли (строки 75–132) — главное

```go
switch role {
case "admin":
    // видит ВСЕ заявки
    rows := h.db.Query(ctx, srSelect+` ORDER BY sr.created_at DESC`)

case "staff":
    specialty := h.staffSpecialty(ctx, userID)        // узнаём специализацию из БД
    cats := specialtyCategories[specialty]            // какие категории ему положены
    rows := h.db.Query(ctx,
        srSelect+` WHERE sr.category = ANY($1) ...`, cats)  // ← фильтр по категориям

default: // resident
    // видит только СВОИ заявки
    rows := h.db.Query(ctx, srSelect+` WHERE sr.user_id = $1 ...`, userID)
}
```

**Три разных запроса в зависимости от роли:**
- **admin** — все заявки.
- **staff** — только заявки своих категорий. `sr.category = ANY($1)` где `$1` —
  массив категорий. `ANY` в SQL = «равно любому из массива» (как `IN`).
- **resident** — только свои (`user_id`).

**Это ответ на «как работает staff-фильтрация»:**
> «Фильтрация на уровне SQL, не в приложении. Мы определяем специализацию сотрудника
> из его профиля, по карте находим разрешённые категории и фильтруем запрос через
> `category = ANY($1)`. Сотрудник физически не получает заявки чужих категорий.»

`srSelect` (строки 46–50) — это `SELECT` с `LEFT JOIN profiles` чтобы подтянуть имя
назначенного сотрудника (`assigned_to_name`).

## 10.3 Take — сотрудник берёт заявку (строки 166–200)

```go
tag, err := h.db.Exec(ctx, `
    UPDATE service_requests
    SET assigned_to=$1, status='in_progress', taken_at=NOW(), updated_at=NOW()
    WHERE id=$2
      AND category = ANY($3)
      AND (assigned_to IS NULL OR assigned_to=$1)
      AND status IN ('new','assigned')`,
    userID, id, cats)

if tag.RowsAffected() == 0 {
    c.JSON(403, gin.H{"error": "request not available..."})
}
```

**Self-assign (берёт на себя).** Условия в `WHERE` защищают от гонки:
- `category = ANY($3)` — только своя специализация.
- `assigned_to IS NULL OR assigned_to=$1` — заявка свободна или уже его.
- `status IN ('new','assigned')` — ещё не в работе/не закрыта.

**`RowsAffected() == 0` — ключевой приём.** Если UPDATE никого не затронул (заявку
уже взял другой, или она не его категории) — значит «не удалось», возвращаем 403.
Это **атомарная проверка-и-захват**: два сотрудника не могут взять одну заявку
одновременно, потому что первый же UPDATE поменяет `assigned_to`, и второй UPDATE
вернёт 0 строк. Обязательно объясни — это защита от race condition без явного замка.

## 10.4 Staff-дашборд (staff.go, строки 30–72) — агрегация одним запросом

```go
SELECT p.id, p.full_name, p.email, p.phone, COALESCE(p.specialty,''),
    COUNT(sr.id) FILTER (WHERE sr.status = 'in_progress')              AS in_progress,
    COUNT(sr.id) FILTER (WHERE sr.status = 'done'
                          AND sr.updated_at >= NOW() - INTERVAL '24h')  AS done_today,
    MAX(sr.taken_at)                                                     AS last_taken_at
FROM profiles p
LEFT JOIN service_requests sr ON sr.assigned_to = p.id
WHERE p.role = 'staff'
GROUP BY p.id
ORDER BY p.full_name
```

Один запрос считает по каждому сотруднику: сколько заявок в работе, сколько закрыл
за сутки, когда последний раз брал. `COUNT(...) FILTER (WHERE ...)` — условный
подсчёт. `LEFT JOIN` — чтобы сотрудники без заявок тоже попали в список (с нулями).
`GROUP BY p.id` — группировка по сотруднику.

**Что сказать:** «Вся аналитика по сотрудникам — один SQL с агрегацией и условными
COUNT через FILTER. Не тянем все заявки в приложение и не считаем в коде — БД делает
это эффективнее».

# ЧАСТЬ 13. СКВОЗНЫЕ ПАТТЕРНЫ (повторяются ВЕЗДЕ — выучи раз)

Если их понять, любой handler читается на автомате. Все handler'ы устроены одинаково.

### Паттерн 1 — структура handler'а
```go
type XHandler struct { db *pgxpool.Pool }
func NewXHandler(db *pgxpool.Pool) *XHandler { return &XHandler{db: db} }
func (h *XHandler) Method(c *gin.Context) { ... }
```
Каждый handler = структура с БД + конструктор `New...` + методы-эндпоинты.

### Паттерн 2 — типичный эндпоинт
```go
func (h *XHandler) Create(c *gin.Context) {
    // 1. проверка роли (если нужно)
    if c.GetString("user_role") != "admin" { forbiddenAccess(c, "admin only"); return }
    // 2. парсинг тела запроса
    var req someReq
    if err := c.ShouldBindJSON(&req); err != nil { c.JSON(400, ...); return }
    // 3. работа с БД
    _, err := h.db.Exec(ctx, `INSERT ...`, req.Field)
    if err != nil { internalError(c, "X.Create", err); return }
    // 4. ответ
    c.JSON(http.StatusCreated, gin.H{"id": id})
}
```
Везде: роль → парсинг → SQL → JSON-ответ. Узнаешь один — узнаешь все.

### Паттерн 3 — `c.ShouldBindJSON` + теги валидации
```go
type createReq struct {
    Category string `json:"category" binding:"required"`
    Email    string `json:"email"    binding:"required,email"`
    Password string `json:"password" binding:"required,min=6"`
}
```
`binding:"required"` — Gin сам проверит, что поле пришло. `email` — что это email,
`min=6` — минимум 6 символов. Если не прошло — `ShouldBindJSON` вернёт ошибку → 400.

### Паттерн 4 — параметризованные запросы (`$1`, `$2`)
```go
h.db.Query(ctx, `SELECT ... WHERE id = $1`, userID)
```
**НИКОГДА не склеиваем строки.** `$1` — placeholder, значение передаётся отдельно,
драйвер экранирует. Это **защита от SQL-инъекций**. Спросят — это твой главный аргумент.

### Паттерн 5 — `QueryRow` vs `Query` vs `Exec`
- `Exec` — для INSERT/UPDATE/DELETE без возврата строк (или с `RowsAffected`).
- `QueryRow` — ожидаем **одну** строку (`.Scan(&x)` заполняет переменные).
- `Query` — ожидаем **много** строк (цикл `for rows.Next() { rows.Scan(...) }`).

### Паттерн 6 — пуши всегда в горутине
```go
go func(id string) { h.notifier.SendToUser(ctx, id, data) }(userID)
```
Сетевые операции (FCM) — в фоне, чтобы не блокировать ответ пользователю.

### Паттерн 7 — проверка на nil перед использованием сервиса
```go
if h.notifier != nil { ... }
```
FCM/MQTT могут быть выключены. Везде проверяем, иначе будет паника (краш).

### Паттерн 8 — обработка ошибок
```go
if errors.Is(err, pgx.ErrNoRows) {
    c.JSON(404, ...)   // не нашли — 404
    return
}
internalError(c, "op", err)  // прочая ошибка — лог + 500
```
`pgx.ErrNoRows` = «запрос не вернул строк». `internalError` (log.go) — логирует
полную ошибку на сервере, а клиенту отдаёт обтекаемое «internal server error»
(не светим детали наружу — безопасность).

### Паттерн 9 — конфигурация через переменные окружения
```go
secret := os.Getenv("JWT_SECRET")
port := os.Getenv("PORT")
if port == "" { port = "8080" }   // значение по умолчанию, если не задано
```
**Никаких паролей/ключей в коде.** Все секреты и настройки читаются из переменных
окружения через `os.Getenv("ИМЯ")`. При локальном запуске они подгружаются из файла
`.env` строкой `godotenv.Load()` в начале `main.go`. Сам `.env` — в `.gitignore`
(не попадает в git).

Какие переменные использует бэк (это «карта конфигурации», полезно знать):
- `DATABASE_URL` — строка подключения к PostgreSQL
- `JWT_SECRET` — секрет для подписи токенов
- `FIREBASE_CREDENTIALS_PATH` — путь к ключу Firebase (если пусто → пуши выключены)
- `HIVEMQ_URL` / `HIVEMQ_USERNAME` / `HIVEMQ_PASSWORD` / `HIVEMQ_CLIENT_ID` — доступ к MQTT-брокеру
- `PORT` — порт HTTP-сервера (по умолчанию 8080)
- `BASE_URL` — базовый адрес для ссылок на загруженные фото

**Ответ на «где у вас хранятся секреты»:** «В переменных окружения, локально — в `.env`,
который в .gitignore. В коде секретов нет. Это 12-factor подход: конфигурация отделена
от кода, для прод/дев можно подставить разные значения без пересборки.»

# ЧАСТЬ 14. КАВЕРЗНЫЕ ВОПРОСЫ ПО КОДУ + ОТВЕТЫ

**В: Почему Go, а не Node.js/Python для такого проекта?**
> «У нас в одном процессе параллельно: HTTP-сервер, MQTT-подписчик, фоновый sweeper,
> SSE-рассылка. Go-горутины делают это легко и дёшево — тысячи горутин на нескольких
> ядрах. В Node.js один event-loop, в Python мешает GIL. Плюс Go компилируется в один
> бинарник без рантайма.»

**В: Что такое горутина и сколько их у вас работает?**
> «Горутина — легковесный поток, управляемый рантаймом Go. Постоянно работают:
> главная горутина HTTP-сервера, по одной на каждое входящее соединение (включая
> SSE), горутина sweeper'а. Плюс на каждый пуш мы спавним короткоживущую горутину,
> чтобы не блокировать обработку. Запустить горутину — `go функция()`.»

**В: Покажите, где у вас защита от SQL-инъекций.**
> Открой любой handler. «Везде параметризованные запросы: `$1`, `$2`, значения
> передаются отдельным аргументом, драйвер pgx их экранирует. Мы нигде не склеиваем
> пользовательский ввод в строку запроса.»

**В: Что если два сотрудника возьмут одну заявку одновременно?**
> Открой `service_requests.go:182`. «UPDATE с условием `status IN ('new','assigned')`
> атомарен. Первый сотрудник меняет статус на in_progress, у второго `RowsAffected`
> вернёт 0 — мы отдадим ему 403. Гонка невозможна без явного замка, сама БД её решает.»

**В: Как вы гарантируете, что событие не создаётся дважды?**
> `mqtt/client.go:171`. «Событие создаётся только при переходе NORMAL→ALERT или
> OFFLINE→ALERT. Повторный ALERT→ALERT игнорируется. Мы читаем предыдущий статус
> перед записью и сравниваем.»

**В: Что произойдёт, если упадёт Firebase?**
> «При старте, если ключ Firebase недоступен, notifier остаётся nil, и сервер
> работает без пушей — везде есть проверки `if notifier != nil`. Если ошибка при
> отправке конкретного пуша — она логируется в горутине и не ломает основной поток.»

**В: Что такое UPSERT и где он у вас?**
> `mqtt/client.go:138` и `sensors/seed.go`. «INSERT ... ON CONFLICT DO UPDATE.
> Атомарно: вставить датчик, а если есть — обновить статус. Один запрос вместо
> SELECT+IF+INSERT/UPDATE, без гонки.»

**В: Почему SSE, а не WebSocket? И как клиент авторизуется в SSE?**
> «SSE — односторонний канал сервер→клиент, нам нужен только он, и он проще
> WebSocket. Авторизация: EventSource не умеет слать заголовки, поэтому токен идёт
> в query `?token=`, и наш middleware (`middleware/auth.go:24`) умеет его оттуда читать.»

**В: Как вы защищаете медленных SSE-клиентов от блокировки рассылки?**
> `sse/hub.go:54`. «У каждого клиента буферизованный канал на 16 фреймов. В Broadcast
> мы пишем через `select` с `default`: если канал полон, фрейм для этого клиента
> отбрасывается, отправитель не ждёт. Один зависший клиент не тормозит остальных.»

**В: Где хранятся пароли и как?**
> `auth.go:47`. «Пароли не хранятся. В БД — bcrypt-хеш с автоматической солью.
> При логине сравниваем через `CompareHashAndPassword`, хеш необратим.»

**В: Что внутри JWT и можно ли его подделать?**
> `auth.go:172`, `middleware/auth.go:32`. «Внутри user_id, email, role, срок 24ч.
> Токен подписан HS256 нашим секретом. Подделать без секрета нельзя — подпись не
> сойдётся, middleware вернёт 401. Авторизация stateless — сессии не храним.»

**В: Как мобильное приложение узнаёт о тревоге мгновенно?**
> «Два механизма. Жителю — FCM push (работает даже когда приложение закрыто, Google
> держит соединение). Админу в открытой панели — SSE в реалтайме. MQTT-сообщение
> триггерит оба: пуш через горутину, SSE через hub.Broadcast.»

**В: Почему last_seen_at обновляется на каждое сообщение, а событие — нет?**
> «last_seen_at — это «жив ли датчик», его надо трогать на каждый heartbeat (раз в
> 30 сек), иначе sweeper посчитает датчик мёртвым. А событие тревоги — только при
> реальном переходе в ALERT, иначе спам. Это разные вещи: liveness vs alarm.»

**В: Что такое RETURNING в ваших запросах?**
> «PostgreSQL-расширение: INSERT/UPDATE сразу возвращает изменённые строки. Например
> в sweeper один UPDATE и помечает датчики OFFLINE, и возвращает их список для пушей.
> Без RETURNING пришлось бы делать отдельный SELECT.»

**В: Чем отличается `*int` от `int` в ваших структурах?**
> «`*int` — указатель, может быть nil. Используем там, где надо отличить «не задано»
> от «ноль». Например `entrance *int`: nil = подъезд не указан, а не «подъезд 0».»

**В: Что такое `ctx context.Context`, который у вас в каждой функции?**
> «Контекст несёт сигнал отмены и дедлайн запроса. Когда клиент отключается, контекст
> запроса закрывается, и связанные операции (запрос к БД, ожидание в SSE) могут
> прерваться досрочно. Мы прокидываем ctx по цепочке вызовов — это стандарт Go для
> управления временем жизни запроса. В фоновых горутинах используем context.Background().»

**В: Что такое `c *gin.Context` и `gin.H`?**
> «`c` — объект запроса Gin: и входящие данные (тело, query, заголовки), и ответ
> (`c.JSON`), и общая память запроса (`c.Set`/`c.GetString`) — через неё middleware
> передаёт user_id в handler. `gin.H` — это просто `map[string]any`, удобная запись
> для сборки JSON-ответа.»

**В: Как именно конкурентность помогает у вас на практике (не в теории)?**
> «Конкретный пример: пришло MQTT-сообщение о тревоге. В handleSensor мы синхронно
> пишем в БД и шлём SSE (это быстро, миллисекунды), а отправку push через Firebase
> (1-2 секунды по сети) запускаем в отдельной горутине через `go func(){...}()`.
> Поэтому приём следующего датчика не ждёт, пока Google доставит пуш. Без горутин
> один медленный пуш тормозил бы всю обработку.»

**В: Что будет, если PostgreSQL временно недоступен?**
> «Запрос вернёт ошибку, handler через `internalError` залогирует её и отдаст клиенту
> 500. Данные не повредятся — мы используем pgxpool (пул соединений) и для связанных
> изменений транзакции (например в шлагбауме): при ошибке Rollback откатывает всё.»

**В: Почему вы читаете user_id из токена, а не из тела запроса?**
> «Тело запроса клиент может подделать — написать чужой user_id. А user_id в токене
> подписан нашим секретом и проверен middleware, ему можно доверять. Поэтому везде
> берём `c.GetString("user_id")` из контекста, заполненного из JWT, а не из JSON.»
